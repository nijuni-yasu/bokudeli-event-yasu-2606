# 誕生日会を増やす仕掛け／貸切イベントの種類／店舗主催の定例イベント設計（ブレストと検討）

「お店で誕生日会はアリ」を前提に、(1) 誕生日会を**したくなる**仕掛け、(2) 誕生日会以外に**貸切したくなる**イベント、(3) **店舗主催の定例イベント**（毎月第四土曜の「XXX PARTY」、最小催行人数＋テーブル開催、参加者グループチャット、開催レポートの掲示板投稿）を検討する。

- 作成日: 2026-10-07
- 関連資料: 02_誕生日会開催サービス検討、04_飲食店を口説くポイント_機能と訴求、01_事業性評価
- **根拠の強さ**: 【確認】公開資料で確認 / 【二次】記事・調査会社の主張 / 【仕様書】shokujii の仕様書に記載（実装状況は未確認）/ 【推論】本書の推測。アイデアの評価（◎○△）は主観の仮置き
- 確度（アイデアの実現しやすさ）: 高＝既存機能の延長／中＝組み合わせ・設計判断が必要／低＝外部連携・法務・効果検証が必要

## 1. 要点

1. **誕生日会が増えない最大の壁は「自分から言い出せない」「幹事が面倒」「人が集まるか不安」の 3 つ**（【推論】）。解決の中心は、**幹事を友達に移す**（祝う側が主催する）ことと、**主催者の負担・金銭リスクをゼロにする**こと。
2. **「店舗主催の月例『BIRTHDAY PARTY』（今月生まれの人が主役）」が、個人の誕生日会への入口になる。** 店が肩代わりした場で「祝われる体験」をしてもらい、翌年に自分で主催してもらう流れ（誕生日会のファネル）。
3. 誕生日会以外の貸切需要は、**人生の節目、推し活、季節行事、仲間の打ち上げ、食体験、子ども・家族、食の制約**の 7 系統で洗い出した（§3）。有力候補は**推し誕・推し会**（推し活市場は約 3.9 兆円【二次】）、**歓送迎会・忘年会**、**アレルギーがあっても安心して祝える子ども・家族の会**。
4. **店舗主催の定例イベントは有望だが、そのままでは 3 つの弱点がある**（§4）: (a) 土曜夜は通常営業で埋まる店が多く「閑散帯を埋める」目的と矛盾しうる、(b) 既存仕様の最小催行人数は **1〜5 名・判定 1 回**でパーティー規模に足りない、(c) 掲示板・チャットは過疎化しやすい（01 の R1）。**曜日・時間は店が選べる**、**最小催行を 3 段階（パーティー → テーブル → 不成立）に拡張**、**チャットはイベント単位・期間限定**にすることで解消する。
5. **営業の一言に加えられる新しい約束**: 「毎月のパーティーデーを、企画・告知・集金・当日リストまで自動で回します」「人数が足りなくても中止にせず、少人数のテーブル開催に切り替えます」。

## 2. 誕生日会を「したくなる」仕掛けのブレスト

### 2.1 まず、なぜ誕生日会が開かれないか（阻害要因）

| # | 阻害要因 | 内容（【推論】） |
| :-- | :-- | :-- |
| I1 | 自分から言い出せない | 自分の誕生日に友達を呼ぶのは気恥ずかしい |
| I2 | 幹事が面倒 | 日程調整、店探し、出欠管理、集金、アレルギー確認 |
| I3 | 人が集まるか不安 | 少人数だと寂しい、断られるのが怖い |
| I4 | お金の気まずさ | 主役が払うのか、割り勘か、いくら集めるか |
| I5 | サプライズ失敗の不安 | 主役にバレる、演出を店に頼む方法が分からない |
| I6 | きっかけがない | 誕生日の直前まで思い出さない、予約が間に合わない |
| I7 | 家で済ませる／祝わない | 外で祝う習慣がない世代・個人 |
| I8 | 店に頼みづらい | 貸切の可否、料金、持ち込み可否が分からない |

調査から分かること: 友達からサプライズされたらうれしい人は約 9 割（高校生 310 人の調査。**対象が高校生で成人には直接当てはまらない**）【二次】。レストランの誕生日プレートは「店に伝えるだけで手軽」と人気とされる【二次】。20 代は SNS・推し活を重視する傾向がある【二次】。推し誕は、公式イベントがなくても平均約 1 万円を使い、5 万円以上使う人もいる【二次】。

### 2.4 注意点

- **他人の誕生日データ（#2）は個人情報**。本人の同意のない登録を前提にしない。初期は本人が登録した誕生日（店の会員など）に限る。
- 子どもの写真・顔の公開は、保護者の同意を前提にする。
- サプライズの内緒モード（#19）は、主役に通知が届かないよう設計に注意する。

## 4. 店舗主催の定例イベントの検討

### 4.1 構想の整理（ご提案の内容）

| # | 要素 | 内容 |
| :-- | :-- | :-- |
| ① | 定例化 | 毎月第四土曜は「XXX PARTY」のように、店が主催して定期開催 |
| ② | 最小催行＋テーブル開催 | 最小催行人数を決めて開催。**人数が足りない場合は、中止せずテーブル開催**にする |
| ③ | 参加者グループチャット | イベントの参加者同士でグループチャット |
| ④ | 開催レポートの掲示板投稿 | 開催の様子をコミュニティの掲示板に投稿し、次の開催につなげる |

**全体の評価**: 4 要素は「**店が自分で回せる集客の仕組み**」として一貫しており、これまでの課題（コミュニティの過疎化、主催者がいない、中止の失望）への有効な打ち手になる。誕生日会（個人主催）への**入口**にもなる（§4.7）。ただし、§4.8 のリスクへの対策が要る。

### 4.2 ① 定例化（毎月第四土曜の「XXX PARTY」）

**良い点**

- 「第四土曜は PARTY」と覚えてもらえる（習慣化）。告知の手間と費用が減る。
- 店のオペレーションと仕込みを平準化できる。
- 主催自動化（シリーズ化・次回の自動下書き）の既存アイデアを使える【仕様書：主催自動化 O-03〜O-05】。

**懸念と対策**

| 懸念 | 対策 |
| :-- | :-- |
| 土曜の夜は通常営業で満席になる店が多く、**閑散帯を埋める目的と矛盾**する（【推論】） | 曜日・時間帯は**店が選ぶ**（第〇△曜、ランチ、早い時間、遅い時間）。「第四土曜」は例とし、店ごとに設定 |
| 連休・祝日・大型イベントと重なる | 例外日の自動シフト（前週・翌週）。店が年間カレンダーで確認できる |
| 毎月の企画がネタ切れする | **年間テーマカレンダー**（§3 の季節行事、食体験）を店のタイプ別に自動提案。参加者のリクエスト投票 |
| 常連だけで固定化し、新規が入りにくい | 初参加の特典、1 人参加歓迎枠、店主による紹介（参加者のチャットでの自己紹介） |
| 店の企画・告知の負担が大きい | **テンプレート**（タイトル・説明・価格・メニュー案・告知文）を自動生成 |

**命名のガイド**: 「〇〇 PARTY」「〇〇 NIGHT」「〇〇会」。ブランドを作ると定着しやすい（例: SAKE NIGHT、BIRTHDAY PARTY（今月生まれ）、CURRY PARTY、VEGAN NIGHT、NEW MENU PREVIEW）。

### 4.3 ② 最小催行人数と「テーブル開催」

**既存仕様との関係（重要）**

- 既存の最小催行人数・自動中止の仕様は、**最小催行人数が 1〜5 名の整数、判定は 1 回、不足時は自動中止して返金**【仕様書】。
- 店舗主催のパーティー（数十名規模）には**そのままでは足りない**。人数の上限（1〜5 名）を拡張し、**段階的な判定**を加える必要がある。

**提案: 3 段階の催行**

| 段階 | 条件 | 開催の形 | 参加者への扱い |
| :-- | :-- | :-- | :-- |
| ① パーティー開催 | 人数 ≥ P 名 | 通常のパーティー（ホール・貸切、企画・演出あり） | 通常どおり |
| ② **テーブル開催** | T 名 ≤ 人数 < P 名 | **同じテーマのコースを、1〜数テーブルで提供**し、参加者が同じテーブルで交流する。演出・企画は縮小 | 事前に内容を明示。差額があれば返金または特典 |
| ③ 不成立 | 人数 < T 名 | 開催せず | **自動で全額返金**、次回の優先案内 |

判定のタイミング: 締切の X 日前（例: 7 日前に 1 回目、3 日前に最終）。段階が②に落ちる可能性は、**申込時に明示**する（「人数が少ない場合はテーブル開催になります」）。

**良い点**: 中止による失望を避けられる。店は中止による売上ゼロを避けられる（少人数でも提供）。参加者は少人数だからこそ会話しやすいという価値がある。

**課題と対策**

| 課題 | 対策 |
| :-- | :-- |
| 期待との落差（パーティーのつもりが小さな食事会になる） | 申込時に②の内容・写真を明示。②になった場合の**差額返金**、または「次回の優先枠」特典 |
| 料理・飲み物の内容が変わる | ②用のコース内容を店が事前に決めておく（原価の調整） |
| テーブル確保が通常客の席を圧迫する | ②は**専用の席数上限**を店が設定。予約が埋まる曜日は② を選ばない（不成立にする）設定 |
| 毎月ずっと②になる | 3 か月続けて②なら、日程・テーマ・価格の見直しを提案する（店のダッシュボードで可視化） |
| 参加者のキャンセル連鎖 | 判定後の参加者の個別キャンセルは不可（既存仕様の「1 回判定」に準ずる）。②に落ちた時点での取消のみ許可 |

### 4.4 ③ 参加者グループチャット

**目的**: 当日前の緊張の緩和、当日の合流、イベント後の関係の継続、再来店。

**リスク**: 荒れる・過疎になる・連絡先の流出・ナンパや勧誘・運営の負担（01 の R1、03 の K3 参照）。

**設計案**

| 項目 | 内容 |
| :-- | :-- |
| 単位・期間 | **イベント単位**。開催 7 日前に開設、開催後 14 日で自動アーカイブ（閲覧のみ） |
| 参加条件 | 参加が確定した人のみ（②のテーブル開催も同様）。ニックネーム可（実名不要） |
| 運営 | **店主またはスタッフが最初の投稿**（歓迎・当日の持ち物・おすすめメニュー）。自動のガイド投稿（自己紹介テンプレート、当日の写真共有の案内） |
| ルール | 営利・勧誘・個人間の連絡先交換の誘導は禁止。通報・ミュート・退出。違反者の店舗での出入り禁止設定 |
| 連絡先 | 個人の連絡先は表示しない。必要なら本人が任意で公開 |
| 既存手段との関係 | LINE のオープンチャットは個人の連絡先リスクと店の管理権限が弱い。**まずは shokujii 内のシンプルなスレッド**（投稿・リアクション中心）で十分 |

**過疎化の対策**: チャットは「雑談の場」ではなく「イベントの連絡と当日の盛り上がり」の場として定義し、**自動ガイド投稿**と**店主の返信**で動かす。リアクションだけでも参加感が出る。

### 4.5 ④ 開催レポートの掲示板投稿 → 次回につなげる

| 項目 | 内容 |
| :-- | :-- |
| 自動生成 | 開催後に、**写真アルバム**（既存のアルバム機能【仕様書】）、参加人数、メニュー、店主のひとことをテンプレートでレポート化 |
| 次回への導線 | レポートの最下段に「**次回: 〇/〇（第四土曜）XXX PARTY あと〇席**」と予約ボタン |
| 同時展開 | Instagram 用の画像・文章を同時に生成（店が投稿するだけ）。開催実績ページとして検索対象（A9）にもする |
| 参加者の参加 | 参加者の投稿（感想・写真）は店の承認制。「次回のテーマ」や「食べたいメニュー」の投票・リクエスト |
| 通知 | 参加者・過去の参加者に、レポートの公開と次回の告知を LINE で通知 |

**注意**

- **写真の肖像権・同意**: 申込時に撮影・掲載の同意を取り、**顔出し不可の選択**を用意する。子どもの写真は保護者の同意が前提。
- **掲示板の過疎化**（01 の R1）: 投稿の主役を**店が担う**（自動生成のレポート）。参加者は読んで反応するだけでよい設計にする。
- 店舗のブランドに関わる投稿は、店が承認してから公開する。

### 4.7 誕生日会との接続（ファネル）

**毎月の「BIRTHDAY PARTY」（今月生まれが主役）**を店舗主催の定例にすると、個人主催の誕生日会の**入口**になる。

```
店舗主催 BIRTHDAY PARTY（毎月）
   今月生まれの人は主役扱い（ケーキ・割引）／友達を連れてきてもよい
          ↓ 「祝われる体験」＋「祝う体験」
 翌年（または別の機会）に、自分の誕生日会を貸切で主催
          ↓
 招待された友達が次の主催者になる
```

| 利点 | 内容 |
| :-- | :-- |
| 気恥ずかしさの解消 | 店が主催する場なら、「自分で呼ぶ」必要がない |
| 幹事の負担の解消 | 参加者は予約するだけ |
| 需要の検証 | 02 資料の最大の未検証事項（誰が主催するか）を、低リスクで測れる |
| 店の売上 | 通常の客より高単価（コース・ケーキ・ドリンク） |
| データ | 誕生日を取得でき、翌年以降の自動案内（#1）に使える |

| 14 | **当日の簡易自己紹介カード・席替えの仕組み** | 初対面の会話を助ける（03 の司会進行のノウハウ） | 高 |
| 15 | **イベント後のリピート特典**（次回の早割、友達同伴の割引） | 再参加を促す | 高 |

## 6. 優先順位と検証の進め方

### 6.1 提案する順序

| 段階 | 内容 | 狙い |
| :-- | :-- | :-- |
| 0 | **店頭の声かけ・既存会員への案内**（開発なし。手動運用）。誕生日会と、店舗主催パーティー 1 回を試験開催 | 需要の有無を実測（誰が主催するか、人数が集まるか） |
| 1 | **店別の貸切ページ＋誕生日会テンプレート**（主役無料割り勘、不成立なら返金） | 個人主催の入口 |
| 2 | **店舗主催シリーズ**（毎月の自動下書き、3 段階の催行、当日進行シート） | 店が自分で回せる集客 |
| 3 | **イベント単位の参加者チャット＋開催レポートの自動投稿** | 次回への導線、実績の蓄積 |
| 4 | 掲示板の常設、サブスク（権利型）、テーマ交流会 | 密度が出てから |

### 6.2 検証計画（1 店舗・3 か月）

| 項目 | 内容（仮置き） |
| :-- | :-- |
| 対象 | 協力店 1〜3 店。月 1 回の店舗主催パーティー（テーマ付き）を 3 回開催 |
| 見る数字 | 参加人数の推移、段階（パーティー／テーブル／不成立）の割合、再参加率、新規比率、売上、チャット投稿数、次回予約率、アンケートの満足度 |
| 誕生日の検証 | 毎月の BIRTHDAY PARTY の参加者のうち、後日「自分の誕生日会を開きたい」と答えた割合 |
| 店の負担 | 企画・告知・当日運営の工数（時間）を記録し、自動化の優先順位を決める |
| 中止基準 | 3 回連続で最小人数に満たない場合は、日程・テーマ・価格を見直し、改善しなければ停止 |

## 7. 営業前の確認事項

1. 既存の**最小催行人数・自動中止**の実装状況と、人数上限（1〜5 名）・段階判定への拡張の工数【仕様書】。
2. **返金時の手数料**（システム利用料 110 円の扱い）と、②テーブル開催への切り替え時の差額返金の会計処理。
3. 店舗側の手数料条件（04 資料 §8）。定例イベントの参加費に対する手数料率。
4. **写真・チャットの規約**（撮影同意、掲載同意、通報、保持期間）。
5. 法務確認（景品表示法の表示、酒類提供と年齢確認、個人情報・要配慮個人情報、出会い関連の規制。03 の K3）。
6. 他人の誕生日データ（#2）の扱い。本人同意のない登録は行わない。

## 8. 注意事項

- 誕生日・貸切イベントの需要評価は**推論**が中心で、日本の成人の誕生日会の実態を示す統計は今回確認できなかった。サプライズの嬉しさを示す調査は対象が高校生で、成人には直接当てはまらない。
- 推し活市場の規模（約 3.9 兆円）、推し誕の平均支出（約 1 万円）は調査会社・記事の数字で、調査方法・対象は未確認。
- アレルギーのある子の誕生日会の需要は**推論**。店のアレルギー対応の体制と事故リスクの確認が先。
- 店舗主催の定例イベントの成功率に関する統計は確認できていない。定例イベントを活用する飲食店の事例はあるが（客足の落ちる時期の集客施策として）、個々の成果の数字は未確認【二次】。
- 評価（◎○△、順位、確度）は主観の仮置き。検証の結果で更新する。
- 法務の記述は一般論で、専門家の確認を代替しない。
