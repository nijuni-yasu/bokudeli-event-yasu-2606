# 飲食店が導入したくなる機能の検討（店舗コミュニティサイト・掲示板・LINE 連携）

飲食店オーナーが次の 7 つを「したくなる」ための機能を検討し、**実装を進めるかの意思決定**に使う資料。

1. shokujii を導入したくなる
2. 飲食店主催でイベントを開催したくなる
3. お客様主催のイベント（貸切パーティ）を促したくなる
4. コミュニティマーケティングをしたくなる
5. 常連客同士の横のつながりで店を繁盛させたくなる
6. LINE などで獲得した顧客情報を活かして、お客さん同士を交流させたくなる
7. 「食事でつながる」shokujii を通じた交流促進が商売繁盛につながる

- 作成日: 2026-10-16
- 前提（依頼で追加された方向性）: **(a) コミュニティ掲示板**（主催者・参加者が自由に投稿し、リアクション・返信ができる。店の普段の様子、イベント告知、情報交換、友達募集。YouTrust・mixi・OKWAVE のコミュニティのイメージ）、**(b) LINE 公式アカウントとの連携**（店は LINE で友だちを集めて CRM に使っている。LINE からコミュニティサイトやイベントを定期配信する）、**(c) 店頭チラシ＋QR** で「掲示板・イベント開催ができるコミュニティサイトを立ち上げました」と案内する
- 根拠: [14_競合調査](../../14_競合調査/00_README.md)（特に [partner への示唆](../../14_競合調査/50_飲食店向けSaaS/05_partnerへの示唆.md)、[コミュニティとロイヤルティ](../../14_競合調査/50_飲食店向けSaaS/04_コミュニティとロイヤルティ.md)、[有力機能の評価](../../14_競合調査/30_機能比較/03_有力機能の評価.md)、[自社 77 機能判定](../../14_競合調査/90_調査ノート原本/03_機能比較と飲食店SaaS調査/26_features_shokujii.md)）と、本フォルダの 00〜07
- **根拠の強さ**: [事実]＝出典・コードで確認／[自社主張]＝ベンダー自身の数値／[推測]＝本書の判断。【実装】＝`origin/main`（v2.14.0）にコードがある／【仕様書】＝仕様書・Issue はあるが未実装／【新規】＝仕様・Issue なし。工数は S（〜1 日）・M（2〜5 日）・L（1 週間〜）の仮置きで、見積もりではない

## 0. 意思決定のための要約

### 0.1 結論（推奨）

**「店舗コミュニティサイト」を 1 店舗 1 ページの単位で立ち上げ、その上に掲示板・店舗主催イベント・お客様主催イベント・LINE 連携を載せる。** 実装は 4 段階に分け、**Phase 0〜1（約 1〜1.5 か月相当の工数。仮置き）で店舗検証に入る**ことを推奨する。

| Phase | 内容 | 狙い | 主な工数 |
| :-- | :-- | :-- | :-- |
| **0 解放** | partner に既にある「店舗主催設定（コミュニティ）」「店舗主催イベント」を、自己承認の禁止（#2452）と店舗選択を直してからナビに出す。店舗コミュニティページを「お店のコミュニティサイト」として整える。QR 付きチラシを店舗向けにし、LINE・Instagram に貼れる配信素材と流入元計測を用意する | **開発を小さく抑えて**、店舗主催イベントと貸切の需要を実店舗で測る | M |
| **1 掲示板** | コミュニティ掲示板（投稿・画像・リアクション・返信、投稿種別、店の承認・通報）。イベント作成・開催レポートから掲示板への自動投稿 | 「店の普段の様子」「告知」「情報交換」の場。過疎化しないよう**自動投稿を主役**にする | L |
| **2 LINE** | LINE ログイン（友だち追加つき）、店の LINE 公式アカウントへのダイジェスト配信（Messaging API）、店舗向け効果レポート | 店が持つ LINE 友だちを、コミュニティとイベントの参加者に変える | L |
| **3 つながり** | 貸切・イベント枠の登録と「このお店で開催する」、誕生月の案内、常連限定枠、ともだち・サブグループ | 常連同士の横のつながりと、お客様主催の貸切を増やす | L |

### 0.2 なぜこの順か（根拠の要点）

- **店舗主催の土台はすでにコードにある。** partner アプリに `店舗主催設定`（店舗にコミュニティを紐づける `shop.community_account`）と `店舗主催イベント` の作成・一覧画面が `origin/main` に存在し、**ナビに出ていないだけ**である [事実]（`partner/src/pages/community.vue`、`partner/src/pages/events/create.vue`。文言「店舗主催設定」「店舗主催イベント」は `partner/src/locales/messages/ja.ts`）。Phase 0 は、この隠れた機能を出して検証することから始められる。ただし**そのまま公開できない前提が 2 つある** [事実]: (1) 3 画面とも `shops[0]`（先頭の店舗）を固定で選び、複数店舗を持つ partner は先頭店舗にしかコミュニティを作れない。(2) `community.vue` は新規コミュニティを `is_approved: true` で作成し、`firestore.rules` は create 時にこの値を制約しないため、運営の承認を経ずにイベント作成へ進める（Issue #2452、v2.15）。この 2 点は Phase 0 の**解放前の必須作業**（§4.1）に含める。
- **店が困っているのは「集客のネタ・継続・時間」。** 飲食店ドットコム会員 393 件の調査（2024-05、東京・単店舗に偏る）で、自店運用の SNS は Instagram 79.1%、LINE 公式 18.1%、悩みはネタ出し 42.5%・フォロワー獲得 41.7%・継続 34.4%・作業時間 31.6% [事実]。**店が自分で投稿し続ける前提の掲示板は過疎化する**（[01 事業性評価](../市場・競合調査/01_事業性評価_一体型コミュニティの成否と対策.md) R1）。だから Phase 1 の掲示板は、イベント・注文・開催後の出来事を**自動で投稿する**設計を主役にし、店の手入力は補助にする。
- **掲示板単体の成長根拠は弱い。** 競合 15 サービスの評価で、グループチャット・掲示板（CR07）は普及度 9 だが根拠は「弱」で、効いたと説明されるのはチャットではなく**卓編成（固定曜日・6 人卓）**である [事実]（[有力機能の評価](../../14_競合調査/30_機能比較/03_有力機能の評価.md) §3.2）。掲示板は「場」としては要るが、**人を集めるのはイベントと LINE 配信**である。この順序で作る。
- **LINE は競合せず、店の既存接点として使う。** LINE 公式の無料枠は月 200 通、ライトは月 5,000 円（5,000 通）[事実]。LINEヤフーはトレタを子会社化し（2026-02-25）、LINE レストランプラス（1 年目実質無料キャンペーン）で配信・CRM を押さえにきている [事実]。shokujii は配信基盤を自前で作らず、**店の LINE 公式に「配信する中身（イベント・掲示板のダイジェスト）」を供給する**側に立つ。
- **収益は成果課金で、店の月額に頼らない。** 日本のポータルは掲載無料・来店課金（3,000 円/人なら約 6.7〜6.8%）[事実・試算]。shokujii の飲食店手数料は現行 3.6%、13.6% への引き上げが Issue #969（v2.15）にある [事実]。店舗コミュニティは**手数料の根拠（送客・貸切成立）を増やす機能**として位置づける。

## 2. 7 つの「したくなる」と機能の対応

各項目で、オーナーの心理 → 阻害要因 → 機能候補 → 根拠 の順に整理する。機能 ID（F-xx）は §3 の一覧と対応する。

### 2.1 shokujii を導入したくなる

| オーナーの心理 | 阻害要因 | 機能候補 |
| :-- | :-- | :-- |
| 売上が増えるなら使いたい。費用は払いたくない。手間は増やしたくない | 「また新しいツールか」「LINE で足りている」「効果が分からない」 | F-01 店舗コミュニティサイトの自動セットアップ、F-02 店舗向けチラシ・QR、F-03 配信素材の自動生成、F-14 効果レポート |

- 口説く一言は [07 飲食店を口説くポイント](../営業・提案/07_飲食店を口説くポイント_機能と訴求.md) の「お客様が、お客様を連れてくる」「初期費用・月額 0 円、成約したときだけ」を使う。
- **導入の瞬間に「もう動いている」状態を見せる**ことが要点 [推測]。店舗登録と同時にコミュニティサイト（URL・QR・チラシ）が出来上がり、最初の店舗主催イベントの下書きが入っている状態にする（F-01）。
- 根拠: 無料から入る個店向けの型（Airリザーブ、Eat App、Perfect Venue）は導入障壁を下げている [事実]。導入後の価値は、店の SNS 運用の負担（ネタ・継続・時間）を減らせるかで説明する [事実→推測]。

### 2.2 飲食店主催でイベントを開催したくなる

| オーナーの心理 | 阻害要因 | 機能候補 |
| :-- | :-- | :-- |
| 閑散日を埋めたい。常連を囲いたい。企画は思いつかない。人が来なかったら赤字 | 企画・告知・集金・当日運営の手間。中止の失望 | F-04 店舗主催イベントの解放、F-05 型（フォーマット）テンプレート、F-06 催行の 3 段階（パーティー／テーブル／不成立）、F-07 開催レポートの自動投稿 |

- 根拠: 事例調査で共通する型は「外部ゲストが主役」「固定日」「閑散帯」「前払い」「名簿の蓄積」（[05](../飲食店主催/05_店舗主催定例イベント検討.md) §12.4）。稲毛屋の日本酒の会（ほぼ毎月火曜、募集開始日時の固定、キャンセル規定）が国内で最も確かな一次事例 [事実]。
- 型は [06 フォーマット案](../飲食店主催/06_飲食店主催イベント_フォーマット案.md) の上位（蔵元の会、おひとり様限定会、新メニュー試食会）を初期テンプレートにする。
- **最小催行人数の拡張（1〜5 名 → 店舗規模、段階判定）は必須**（[05](../飲食店主催/05_店舗主催定例イベント検討.md) R10）。

### 2.3 お客様主催のイベント（貸切パーティ）を促したくなる

| オーナーの心理 | 阻害要因 | 機能候補 |
| :-- | :-- | :-- |
| 常連が友達を連れて貸切にしてくれるなら歓迎。でも繁忙日や変な客は困る | 貸切の条件（日時・人数・最低消費額）を伝える手段がない。主催者側の幹事負担 | F-10 貸切・イベント枠の登録、F-11 「このお店で開催する」導線、F-12 誕生月の案内、F-06（主催者側の不成立返金） |

- 根拠: SevenRooms の Event Management（最低消費額を曜日・時間・部屋・人数で設定、未成約枠の解放）が海外の型 [事実]。日本の主要ポータルには貸切の専用販売機能が確認できず、**最小催行人数・不成立時の返金はどのサービスでも確認できなかった空白** [事実]。
- 「店舗が自店のファンを幹事側に変える導線」の既存事例は見つかっていない [事実]。これは差別化であり、同時に**需要が未検証**という意味でもある。[03 誕生日開催](../誕生日開催/03_誕生日開催サービス_総合.md) の手動検証（店頭の声かけ・既存会員への案内）を Phase 0 で行う。

### 2.4 コミュニティマーケティングをしたくなる

| オーナーの心理 | 阻害要因 | 機能候補 |
| :-- | :-- | :-- |
| 常連に情報を届けたい。新規にも広めたい。投稿は続かない | ネタ出し・継続・時間（調査で上位の悩み） | F-08 コミュニティ掲示板、F-09 自動投稿（イベント作成・満席・開催レポート・新メニュー）、F-03 配信素材、F-13 LINE 配信 |

- 掲示板の投稿種別は OKWAVE のコミュニティに倣い **トーク／お知らせ／イベント／募集（Q&A）** とし、店の「お知らせ」と自動投稿が土台になるようにする [事実（OKWAVE の種別: トーク・Q&A・お知らせ・アンケート）→推測]。
- 「投稿すれば反応がある」状態を作るため、リアクション（既存チャットの絵文字リアクションを流用）と返信を最初から入れる。

### 2.5 常連客同士の横のつながりで繁盛させたくなる

| オーナーの心理 | 阻害要因 | 機能候補 |
| :-- | :-- | :-- |
| 常連が仲良くなれば店が居場所になる。ただし内輪化や新規の疎外は怖い | 常連が固まりすぎる（パーラー305 の例）。出会い目的・勧誘の持ち込み | F-15 ともだち・共通イベント履歴（既存の「ともだち」を店舗単位で表示）、F-16 常連限定枠・初来店限定枠、F-17 サブグループ、F-18 通報・ブロック・出入り禁止 |

- 根拠: 既存の「ともだち」（同じ食事会に参加した相手が自動で蓄積、食事した回数順）[事実・実装] は、横のつながりの可視化にそのまま使える。
- 「常連限定」と「一般募集」を使い分ける稲毛屋の型、常連で埋まって新規が入りにくくなったパーラー305 の型 [事実] から、**常連枠と新規枠の両方**を持つ。
- 出会いは前面に出さない。男女別の限定会やプロフィール公開は扱わない（[02 街コン](../市場・競合調査/02_街コン市場と店コン検討.md) K3）。

### 2.6 LINE などで獲得した顧客情報を活かして交流させたくなる

| オーナーの心理 | 阻害要因 | 機能候補 |
| :-- | :-- | :-- |
| LINE の友だちは何百人もいる。配信しても一方通行で反応が薄い | LINE は店→客の一方向。友だち同士はつながれない。通数に費用がかかる | F-03 配信素材、F-13 LINE 公式への配信連携、F-19 LINE ログイン（友だち追加つき）、F-20 店頭 QR からの LINE 友だち追加＋コミュニティ参加 |

- 根拠: LINE 公式は無料プランで月 200 通、ライトは月 5,000 円で 5,000 通 [事実]。店の LINE 友だちが数百人なら、**月 1〜4 回の配信**に収まる設計が要る。
- 店の LINE 友だちは **LINE 上の識別子**であり、shokujii のユーザーとは別。本人の操作（LINE ログイン、友だち追加後のリンクタップ）で結びつける。店の友だちリストを shokujii に取り込む形は取らない（個人情報・LINE の規約）。
- LINE ログインは Firebase Auth の標準プロバイダにないため、Functions でのカスタムトークン発行が要る（工数 L）。JN02 の簡易ログインの根拠は「弱」で、成長の決め手ではない [事実]。**配信素材 → LINE ログイン → Messaging API** の順で深める。

### 2.7 「食事でつながる」交流促進が商売繁盛につながる

| オーナーの心理 | 阻害要因 | 機能候補 |
| :-- | :-- | :-- |
| 交流が売上になる実感がほしい | 効果が見えない。手数料の根拠が分からない | F-14 効果レポート（イベント売上、新規比率、再来店、ポータル手数料との比較）、F-07 開催レポート |

- 根拠: TableCheck・Owner.com は手数料の削減額を前面に出す [自社主張]。shokujii は「幹事経由の来店人数・売上」「閑散帯の充填」「ポータルの来店課金（約 6.7%）との比較」を店ごとに出す。比較表現は自社の手数料水準の確定が前提（D5）。
- 「交流が売上に効く」第三者検証済みの数値は見つかっていない [事実]。だから **自社の検証（§6）で数字を作る**ことが、この項目の実体である。

### 3.2 店舗コミュニティサイトの構成（Phase 0〜1 の完成形）

```
/c/{店舗の community_account}（既存のコミュニティ公開ページを拡張）
├─ ヘッダー: 店名・カバー・紹介・「メンバーになる」・LINE 友だち追加

│    └─ 投稿: 本文・画像・リアクション・返信。店の投稿はピン留め可
├─ イベント: 店舗主催（Phase 0）／お客様主催（Phase 3、店舗で開催されるイベント）
```

店舗（partner）側は、既存の「店舗主催設定」「店舗主催イベント」に加えて、**掲示板の管理（承認・削除・ピン留め）**、**配信素材**、**効果レポート**のタブが増える。

### 3.3 掲示板の設計要点

| 項目 | 設計 | 理由 |
| :-- | :-- | :-- |
| 投稿できる人 | 店（管理者）とメンバー。初期設定は**店の承認後に公開**。店は「承認なし」に切り替えられる | 荒らし・勧誘の防止。店のブランドを守る（R5・K3） |
| 投稿種別 | トーク／お知らせ／イベント／募集。「お知らせ」は店のみ | OKWAVE の種別に倣う。募集（友達募集・同行者募集）は Phase 1 では**店が許可した場合のみ** |
| 自動投稿 | イベント公開・残席わずか・満席・開催レポート・新メニュー・（売り切れ解除）を「お知らせ」として自動投稿 | 店の手入力なしで掲示板が動く |
| リアクション・返信 | 絵文字リアクション（既存チャットの実装を流用）、返信は 1 階層 | 「反応がある」体験を最初から |
| 通知 | メンバーへは週次ダイジェスト（既存のメール・将来の LINE）に掲示板の新着を含める。投稿ごとの即時通知はしない | 通知疲れと LINE 通数の抑制 |
| 公開範囲 | 掲示板は**メンバー限定で閲覧**を初期値とし、店が「誰でも閲覧」に切り替えられる | 店の普段の様子をメンバー特典にする。SEO 流入が欲しい店は公開 |
| 安全 | 通報・ブロック・店の削除・出入り禁止。営利・勧誘・出会い目的の禁止を規約と投稿画面に明記 | TS03 の実装を本フェーズに前倒し |
| データ | コミュニティ配下の `posts` サブコレクション（投稿）と `replies`、リアクションは既存チャットの構造を参考に | Firestore Rules・インデックスは別途設計 |

**チャット（#2217）との関係**: チャットは「流れる会話」、掲示板は「残る投稿」。店舗コミュニティで店が求めるのは後者（告知・様子・募集が後から読める）と判断し、**店舗コミュニティでは掲示板を採用し、#2217 のコミュニティチャットは主催者コミュニティ向けのまま進める**（D2）。実装では、投稿の添付・リアクション・通報は既存チャットの部品を再利用する。

### 3.4 LINE 連携の段階

| 段階 | 内容 | 店の作業 | shokujii の実装 | 費用・法務 |
| :-- | :-- | :-- | :-- | :-- |
| L0（Phase 0） | 配信素材の自動生成（画像＋文面＋リンク）。店が LINE 公式・Instagram に手で貼る | 月 1〜4 回の貼り付け | S〜M | 店の通数のみ |
| L1（Phase 2） | 店頭 QR → LINE 友だち追加 → コミュニティ参加の導線。LINE ログイン | — | L（カスタム認証） | LINE ログインの審査・プライバシーポリシー更新 |
| L2（Phase 2） | 店の LINE 公式のチャネルアクセストークンを partner で登録し、週次ダイジェスト（新着イベント・掲示板・開催レポート）を Messaging API で配信 | トークン登録、配信頻度の選択 | L | 店の通数（無料枠 200 通/月を超えると有料）。トークンの保管（Secret）。配信内容の同意 |

### 3.5 お客様主催イベント（貸切）の権限モデル

既存のモデルは「コミュニティの管理者がイベントを作る」。店舗コミュニティの**メンバーがそのコミュニティ内でイベントを作れる**ようにすると、権限・Rules・請求の設計が大きく変わる。推奨は次の形（D3）。

1. 店舗コミュニティページに「**このお店で開催する**」ボタンを置く（F-11）。
2. 押すと、お客様自身のコミュニティ（なければ作成）でイベント作成に入り、**店舗が初期選択**され、店の貸切枠（F-10）の条件が表示される。
3. 公開されたイベントは、店舗の承認（既存の予約申請）後に、**店舗コミュニティの掲示板へ「イベント」として自動告知**される。
4. 店舗コミュニティページの「イベント」タブには、店舗主催とお客様主催の両方が並ぶ（「この店で開催されるイベント」）。

これで既存の権限モデルを変えずに、「店のコミュニティで客が主催する」体験を作れる。

| 飲食店手数料 | 3.6%（13.6% へ引き上げは #969・v2.15） | 店舗主催・お客様主催の両方で発生。店舗コミュニティは手数料の根拠（送客・貸切）を増やす |
| 参加者のシステム利用料 | 1 決済 110 円 | 変更なし |
| 主催者の請求書払い手数料 | 10% | 店舗主催は店が主催者。請求書払いは使わず、参加者の事前決済が基本 |
| 店舗向け月額 | なし | 作らない（§4.5）。将来の有料オプション候補は F-14 の詳細レポート・LINE 配信の上限拡張 |

**手数料の説明**: ポータルの来店課金は 3,000 円/人で約 6.7〜6.8% [試算]。13.6% は高く見えるため、「幹事経由（お客様主催）」と「店の自力（店舗主催）」で率を分ける案（ストアカの自己集客 10%／送客 30%）を検討する [推測]。検証中は現行 3.6% のまま、検証結果で決める（D5）。
