# 店舗主催の定例イベント検討（毎月の「XXX PARTY」・最小催行＋テーブル開催・参加者チャット・開催レポート）

お店が主催する定例イベント（例: 毎月第四土曜は「XXX PARTY」）を、shokujii の機能としてどう設計するかの検討。

- 作成日: 2026-10-08
- 関連資料: [03 誕生日開催サービス 総合](../誕生日開催/03_誕生日開催サービス_総合.md)（BIRTHDAY PARTY による誕生日会へのファネル、名称）／[04 貸切イベント案（誕生日以外）](../誕生日開催/04_貸切イベント案_誕生日以外.md)（年間テーマカレンダーの素材）／[07 飲食店を口説くポイント](../営業・提案/07_飲食店を口説くポイント_機能と訴求.md)（営業の一言）／[01 事業性評価](../市場・競合調査/01_事業性評価_一体型コミュニティの成否と対策.md)／[02 店コン](../市場・競合調査/02_街コン市場と店コン検討.md)
- **根拠の強さ**: 【仕様書】shokujii の仕様書に記載（実装状況は未確認）／【二次】記事の主張／【推論】本書の推測。評価・確度は主観の仮置き
- 確度（実現しやすさ）: 高＝既存機能の延長／中＝組み合わせ・設計判断が必要／低＝外部連携・法務・効果検証が必要

## 1. 要点

1. 店舗主催の定例イベントは、**店が自分で回せる集客の仕組み**として有望。ただし、そのままでは 3 つの弱点がある。
   - (a) 土曜夜は通常営業で埋まる店が多く、「閑散帯を埋める」目的と矛盾しうる
   - (b) 既存仕様の最小催行人数は **1〜5 名・判定 1 回**で、パーティー規模に足りない【仕様書】
   - (c) 掲示板・チャットは過疎化しやすい（01 の R1）
2. 解決の方向は、**曜日・時間を店が選べる**、**最小催行を 3 段階（パーティー → テーブル → 不成立）に拡張**、**チャットはイベント単位・期間限定**、**開催レポートは店が主役の自動投稿**。
3. **毎月の「BIRTHDAY PARTY」（今月生まれが主役）が、個人の誕生日会への入口になる**（§8）。誕生日会の供給（年 1 回問題）を補う役割も担う（03 §9）。
4. **営業の一言**: 「毎月のパーティーデーを、企画・告知・集金・当日リストまで自動で回します」「人数が足りなくても、中止にせず少人数のテーブル開催に切り替えます」。
5. **事例調査（§12）と店舗主催を増やす方法（§13）**: 国内外の事例に共通する型は、**外部ゲストが主役／固定日／閑散帯／前払いと名簿**。店舗主催が増えない最大の壁は「企画・手間・続かない」と推論され、**型のパッケージ配布＋最初の 3 回の伴走**、最小催行・事前決済によるリスク解消、運営の自動化を優先する。

## 2. 構想の整理

| # | 要素 | 内容 |
| :-- | :-- | :-- |
| ① | 定例化 | 毎月第四土曜は「XXX PARTY」のように、店が主催して定期開催 |
| ② | 最小催行＋テーブル開催 | 最小催行人数を決めて開催。**人数が足りない場合は、中止せずテーブル開催**にする |
| ③ | 参加者グループチャット | イベントの参加者同士でグループチャット |
| ④ | 開催レポートの掲示板投稿 | 開催の様子をコミュニティの掲示板に投稿し、次の開催につなげる |

**全体の評価**: 4 要素は「店が自分で回せる集客の仕組み」として一貫しており、これまでの課題（コミュニティの過疎化、主催者がいない、中止の失望）への有効な打ち手になる。誕生日会（個人主催）への入口にもなる（§8）。ただし §9 のリスクへの対策が要る。

## 3. ① 定例化（毎月第四土曜の「XXX PARTY」）

**良い点**

- 「第四土曜は PARTY」と覚えてもらえる（習慣化）。告知の手間と費用が減る。
- 店のオペレーションと仕込みを平準化できる。
- 主催自動化（シリーズ化・次回の自動下書き）の既存アイデアを使える【仕様書：主催自動化 O-03〜O-05】。

**懸念と対策**

| 懸念 | 対策 |
| :-- | :-- |
| 土曜の夜は通常営業で満席になる店が多く、**閑散帯を埋める目的と矛盾**する（推論） | 曜日・時間帯は**店が選ぶ**（第〇△曜、ランチ、早い時間、遅い時間）。「第四土曜」は例とし、店ごとに設定 |
| 連休・祝日・大型イベントと重なる | 例外日の自動シフト（前週・翌週）。店が年間カレンダーで確認できる |
| 毎月の企画がネタ切れする | **年間テーマカレンダー**（[04](../誕生日開催/04_貸切イベント案_誕生日以外.md) の季節行事・食体験）を店のタイプ別に自動提案。参加者のリクエスト投票 |
| 常連だけで固定化し、新規が入りにくい | 初参加の特典、1 人参加歓迎枠、店主による紹介（参加者のチャットでの自己紹介） |
| 店の企画・告知の負担が大きい | **テンプレート**（タイトル・説明・価格・メニュー案・告知文）を自動生成 |

**命名のガイド**: 「〇〇 PARTY」「〇〇 NIGHT」「〇〇会」。ブランドを作ると定着しやすい（例: SAKE NIGHT、BIRTHDAY PARTY（今月生まれ）、CURRY PARTY、VEGAN NIGHT、NEW MENU PREVIEW）。

## 4. ② 最小催行人数と「テーブル開催」

**既存仕様との関係（重要）**

- 既存の最小催行人数・自動中止の仕様は、**最小催行人数が 1〜5 名の整数、判断は注文期限の 1〜5 日前の 1 回、不足時は自動中止して返金**【仕様書】。
- 店舗主催のパーティー（数十名規模）には**そのままでは足りない**。人数の上限（1〜5 名）を拡張し、**段階的な判定**を加える必要がある。

**提案: 3 段階の催行**

| 段階 | 条件 | 開催の形 | 参加者への扱い |
| :-- | :-- | :-- | :-- |
| ① パーティー開催 | 人数 ≥ P 名 | 通常のパーティー（ホール・貸切、企画・演出あり） | 通常どおり |
| ② **テーブル開催** | T 名 ≤ 人数 < P 名 | **同じテーマのコースを、1〜数テーブルで提供**し、参加者が同じテーブルで交流する。演出・企画は縮小 | 事前に内容を明示。差額があれば返金または特典 |
| ③ 不成立 | 人数 < T 名 | 開催せず | **自動で全額返金**、次回の優先案内 |

判定のタイミング: 締切の X 日前（例: 7 日前に 1 回目、3 日前に最終）。段階が②に落ちる可能性は、**申込時に明示**する（「人数が少ない場合はテーブル開催になります」）。

**良い点**: 中止による失望を避けられる。店は中止による売上ゼロを避けられる。参加者は少人数だからこそ会話しやすいという価値がある。

**名称との対応**: 03 §12 の有力案を当てはめると、①＝**バースミキサー**（大型）、②＝**バースデーテーブル**（少人数）。誕生日以外のテーマでは、①「〇〇 PARTY」、②「〇〇 TABLE」のように揃える案も考えられる。

**課題と対策**

| 課題 | 対策 |
| :-- | :-- |
| 期待との落差（パーティーのつもりが小さな食事会になる） | 申込時に②の内容・写真を明示。②になった場合の**差額返金**、または「次回の優先枠」特典 |
| 料理・飲み物の内容が変わる | ②用のコース内容を店が事前に決めておく（原価の調整） |
| テーブル確保が通常客の席を圧迫する | ②は**専用の席数上限**を店が設定。予約が埋まる曜日は②を選ばない（不成立にする）設定 |
| 毎月ずっと②になる | 3 か月続けて②なら、日程・テーマ・価格の見直しを提案（ダッシュボードで可視化） |
| 参加者のキャンセル連鎖 | 判定後の参加者の個別キャンセルは不可（既存仕様の「1 回判定」に準ずる）。②に落ちた時点での取消のみ許可 |

## 5. ③ 参加者グループチャット

**目的**: 当日前の緊張の緩和、当日の合流、イベント後の関係の継続、再来店。

**リスク**: 荒れる・過疎になる・連絡先の流出・ナンパや勧誘・運営の負担（01 の R1、02 の K3）。

**設計案**

| 項目 | 内容 |
| :-- | :-- |
| 単位・期間 | **イベント単位**。開催 7 日前に開設、開催後 14 日で自動アーカイブ（閲覧のみ） |
| 参加条件 | 参加が確定した人のみ（②のテーブル開催も同様）。ニックネーム可（実名不要） |
| 運営 | **店主またはスタッフが最初の投稿**（歓迎・当日の持ち物・おすすめメニュー）。自動のガイド投稿（自己紹介テンプレート、当日の写真共有の案内） |
| ルール | 営利・勧誘・個人間の連絡先交換の誘導は禁止。通報・ミュート・退出。違反者の店舗での出入り禁止設定 |
| 連絡先 | 個人の連絡先は表示しない。必要なら本人が任意で公開 |
| 既存手段との関係 | LINE のオープンチャットは個人の連絡先リスクと店の管理権限が弱い。**まずは shokujii 内のシンプルなスレッド**（投稿・リアクション中心）で十分 |

**過疎化の対策**: チャットは「雑談の場」ではなく「イベントの連絡と当日の盛り上がり」の場として定義し、**自動ガイド投稿**と**店主の返信**で動かす。リアクションだけでも参加感が出る。

## 6. ④ 開催レポートの掲示板投稿 → 次回につなげる

| 項目 | 内容 |
| :-- | :-- |
| 自動生成 | 開催後に、**写真アルバム**（既存のアルバム機能【仕様書】）、参加人数、メニュー、店主のひとことをテンプレートでレポート化 |
| 次回への導線 | レポートの最下段に「**次回: 〇/〇（第四土曜）XXX PARTY あと〇席**」と予約ボタン |
| 同時展開 | Instagram 用の画像・文章を同時に生成（店が投稿するだけ）。開催実績ページとして検索対象にもする（07 の A9） |
| 参加者の参加 | 参加者の投稿（感想・写真）は店の承認制。「次回のテーマ」や「食べたいメニュー」の投票・リクエスト |
| 通知 | 参加者・過去の参加者に、レポートの公開と次回の告知を LINE で通知 |

**注意**

- **写真の肖像権・同意**: 申込時に撮影・掲載の同意を取り、**顔出し不可の選択**を用意する。子どもの写真は保護者の同意が前提。
- **掲示板の過疎化**（01 の R1）: 投稿の主役を**店が担う**（自動生成のレポート）。参加者は読んで反応するだけでよい設計にする。
- 店舗のブランドに関わる投稿は、店が承認してから公開する。

## 8. 誕生日会との接続（BIRTHDAY PARTY のファネル）

**毎月の「BIRTHDAY PARTY」（今月生まれが主役）**を店舗主催の定例にすると、個人主催の誕生日会の**入口**になる。

```
店舗主催 BIRTHDAY PARTY（毎月）
   今月生まれの人は主役扱い（ケーキ・割引）／友達を連れてきてもよい
          ↓ 「祝われる体験」＋「祝う体験」
 翌年（または別の機会）に、自分の誕生日会を貸切で主催
          ↓
 招待された友達が次の主催者になる
```

| 利点 | 内容 |
| :-- | :-- |
| 気恥ずかしさの解消 | 店が主催する場なら、「自分で呼ぶ」必要がない |
| 幹事の負担の解消 | 参加者は予約するだけ |
| 需要の検証 | 03 の U1（誰が自分で主催するか）を、低リスクで測れる |
| 供給の安定 | 個人主催が年 1 回しかできない問題（03 §9）を、店が毎月開くことで補う |
| 店の売上 | 通常の客より高単価（コース・ケーキ・ドリンク） |
| データ | 誕生日を取得でき、翌年以降の自動案内（03 の #1）に使える |

| # | リスク | 発生可能性 | 対策 |

## 12. 事例調査: 飲食店が主催するイベント

### 12.1 調査の範囲と根拠の強さ

- 国内の個店について、**イベントの成果を数字で示した公開事例はほとんど見つからなかった**。国内は「どんなイベントを、どの頻度で、どんな形で開いているか」という**型**の確認が中心。
- 海外（米国のブルワリー・サパークラブ・予約チケット）は、数字つきの記述もあるが、**マーケティング記事・業界ブログ経由で、一次情報は未確認**のものが多い。
- 「飲食店がイベントを開催しない理由」を示すアンケート統計は、今回の検索では見つからなかった（§13 の阻害要因は推論）。

## 13. 店舗主催を増やす方法

### 13.1 店舗主催が増えない理由（仮説）

事例調査（§12）や飲食店の一般的な事情からの**推論**。やらない理由のアンケート統計は確認できていない。

| # | 阻害要因 | 内容 |
| :-- | :-- | :-- |
| B1 | 企画が思いつかない・ネタ切れ | 何を、どの価格で、どんな日程でやればよいか分からない |
| B2 | 集客できる自信がない | 告知（SNS・チラシ）が苦手。人が集まらなかったときが怖い |
| B3 | 手間が大きい | 企画・告知・予約管理・集金・当日運営・片付け |
| B4 | 赤字のリスク | 仕込み・ゲスト謝礼・人件費が回収できない |
| B5 | 通常営業との両立 | 人手・席の確保。繁忙日とぶつかる |
| B6 | 続かない | 最初だけで、数回で終わる（担当・習慣がない） |
| B7 | 効果が見えない | 売上や常連化にどれだけ効いたか分からない |
| B8 | ゲストとのつながりがない | 蔵元・生産者・シェフ・DJ・MC を探す方法が分からない |
| B9 | ツールがない | チケット販売・名簿・告知・レポートを一元管理できない |

### 13.2 増やすための施策

| # | 施策 | 内容 | 対応する阻害要因 | 確度 |
| :-- | :-- | :-- | :-- | :-- |
| L1 | **イベントの「型」をパッケージで配る** | ワイン会、蔵元の会、ゲストシェフ回、トリビア、月例 BIRTHDAY PARTY などを、企画書・告知文・価格目安・メニュー案・当日台本・必要物品つきで用意。店は選んで日付を決めるだけ | B1、B3 | 高 |
| L2 | **外部ゲストとのマッチング** | 蔵元・生産者・醸造家・ゲストシェフ・DJ・ミュージシャン・MC を shokujii に登録し、店に紹介（店からのオファー、ゲストからの提案の両方）。**ゲストのファンが客を連れてくる**（P1） | B2、B8 | 中 |
| L3 | **集客を肩代わりする** | 既存会員・過去の参加者への自動案内、店別・イベント別の検索ページ、Instagram 用の画像と文章の自動生成、開催レポートからの次回導線（§6）、無料ポータルへの掲載 | B2 | 中 |
| L4 | **リスクを消す** | 最小催行人数＋テーブル開催（§4）、**事前決済**（P5。ノーショーを減らし仕込みを確定）、初回の損失を shokujii が補う**ゼロリスク保証**（最小参加者を shokujii が集める） | B4 | 中 |
| L5 | **運営の自動化** | 年間カレンダーからのシリーズ自動作成、当日進行シート、レポート自動投稿、アンケート自動送信（§7） | B3、B6 | 高 |
| L6 | **「小さく始める」設計** | 既存の席の中で 6〜8 名のカウンター貸切（シェフズテーブル）、追加料金なしの低ハードル型（P4）、最初は月 1 回、閑散日のみ | B4、B5 | 高 |
| L7 | **効果の可視化** | イベント別のダッシュボード（売上、新規客比率、再来店率、名簿増加数、工数）、通常営業の同曜日との比較。「続けた店の成果」の事例ページ | B7、B6 | 中 |
| L8 | **店へのインセンティブ** | 初期店舗は手数料 0%、掲載優先、「定例イベント続けている店」の特集ページ、開催回数バッジ、店→店の紹介特典（既存の紹介プログラム【仕様書】） | B6、B7 | 高 |
| L9 | **共同開催・横展開** | 近隣店のハシゴ（1 次会・2 次会）、複数店の共同企画で負担を分担、商店街・業界団体の既存イベント（「第四土曜日」のような地域イベント）に参加店舗として入る、自治体の補助の活用（未調査） | B2、B3 | 低〜中 |
| L10 | **習慣化の伴走** | 最初の 3 回は shokujii が伴走（企画・告知・当日の同席）。固定日・ブランド名（「〇〇 PARTY」）・担当者を最初に決める（P2、P8） | B6 | 高 |
| L11 | **参加者の声を店の企画に変える** | 「このお店でこんな会がしたい」のリクエスト・投票。需要が可視化されたテーマを店に提案（誕生日など参加者主催の需要→店主催への転換。03 §9 の供給設計とも接続） | B1、B2 | 中 |
| L12 | **全店一斉のキャンペーン** | 忘年会週間、ハロウィン、年度替わりなど、年数回「PARTY WEEK」を設け、参加店が一斉に告知（店の参加動機と集客の双方） | B1、B2 | 中 |
| L13 | **データに基づく提案** | 店の過去の閑散日、会員の誕生月の分布、季節から、「この日にこのテーマを」と自動提案 | B1、B5 | 中 |

### 13.3 優先順位

| 順位 | 施策 | 理由 |
| :-- | :-- | :-- |
| 1 | **L1 型のパッケージ＋L10 伴走**（最初の 3 回） | 最大の障壁（企画・手間・続かない）に直接効き、開発の負担が小さい。まず手動で提供できる |
| 2 | **L4 リスクを消す**（最小催行＋テーブル開催＋事前決済） | 赤字・人が集まらない恐れを消す。既存仕様の拡張（§4） |
| 3 | **L5 運営の自動化** | 毎月続けるための前提。シリーズ・進行シート・レポート |
| 4 | **L2 外部ゲストのマッチング** | 集客を相手のファンに任せられ、国内外の事例で共通（P1）。ただし供給側（ゲスト）の開拓が要る |
| 5 | **L7 効果の可視化＋L8 インセンティブ** | 続ける動機になる |
| 6 | L3 集客の肩代わり、L11 参加者の声、L12 全店キャンペーン | 店数・会員数がある程度ないと効きにくい |

**最初の一手（提案）**: 協力店 3〜5 店を選び、**L1 の型（例: 蔵元の会／ワイン会／月例 BIRTHDAY PARTY のいずれか）を店が選び、最初の 3 回を shokujii が伴走**する。外部ゲストは shokujii が紹介する（L2 の手動版）。これで「企画」「手間」「続かない」の 3 つを同時に検証できる（§14 の検証計画に組み込む）。

### 13.4 見る指標

| 指標 | 内容 |
| :-- | :-- |
| 開催店舗率 | 導入店のうち、月 1 回以上、店舗主催イベントを開いた店の割合 |
| 継続率 | 3 か月連続で開催した店の割合（B6 の指標） |
| 1 回あたり参加人数・段階の割合 | パーティー／テーブル／不成立（§4） |
| 企画・運営の工数 | 店の工数（時間）。自動化の優先順位に使う |
| 新規客比率・再来店率・名簿の増加数 | 効果の指標（P6） |
| ゲスト経由の参加者数 | L2 の効果 |

### 13.5 注意点

- **外部ゲストのマッチング（L2）**: ゲストへの謝礼・手数料の扱い、酒類のメーカー・蔵元が提供する場合の費用負担や表示（景品表示法、酒類に関する規制）、ゲストの肖像・出演の権利を確認する。
- **事前決済チケット（L4）**: 店が売主として販売し、shokujii が代金を預からない構成にする（資金決済法の整理は 03 §15 を参照）。
- **ゼロリスク保証**: 補塡の条件・上限を明確にし、**不正（身内での水増し参加）**を防ぐ設計が要る。
- **共同開催・自治体の補助（L9）**は、今回調査していない。

## 14. 進め方と検証

### 14.1 提案する順序

| 段階 | 内容 | 狙い |
| :-- | :-- | :-- |
| 0 | **店頭の声かけ・既存会員への案内**（開発なし。手動運用）。店舗主催パーティー 1 回を試験開催 | 需要の有無を実測（人数が集まるか） |
| 1 | **店舗主催シリーズ**（毎月の自動下書き、3 段階の催行、当日進行シート） | 店が自分で回せる集客 |
| 2 | **イベント単位の参加者チャット＋開催レポートの自動投稿** | 次回への導線、実績の蓄積 |
| 3 | 掲示板の常設、サブスク（権利型）、テーマ交流会 | 密度が出てから |

### 14.2 検証計画（1 店舗・3 か月）

| 項目 | 内容（仮置き） |
| :-- | :-- |
| 対象 | 協力店 1〜3 店。月 1 回の店舗主催パーティー（テーマ付き）を 3 回開催 |
| 見る数字 | 参加人数の推移、段階（パーティー／テーブル／不成立）の割合、再参加率、新規比率、売上、チャット投稿数、次回予約率、アンケートの満足度 |
| 誕生日の検証 | 毎月の BIRTHDAY PARTY の参加者のうち、後日「自分の誕生日会を開きたい」と答えた割合 |
| 店の負担 | 企画・告知・当日運営の工数（時間）を記録し、自動化の優先順位を決める |
| 中止基準 | 3 回連続で最小人数に満たない場合は、日程・テーマ・価格を見直し、改善しなければ停止 |

## 15. 営業・開発前の確認事項

1. 既存の**最小催行人数・自動中止**の実装状況と、人数上限（1〜5 名）・段階判定への拡張の工数【仕様書】。
2. **返金時の手数料**（システム利用料 110 円の扱い）と、②テーブル開催への切り替え時の差額返金の会計処理。
3. 店舗側の手数料条件（07 §8 #1）。定例イベントの参加費に対する手数料率。
4. **写真・チャットの規約**（撮影同意、掲載同意、通報、保持期間）。
5. 法務確認（景品表示法の表示、酒類提供と年齢確認、個人情報・要配慮個人情報、出会い関連の規制。02 の K3）。
6. 「テーブル開催」の用語整理（03 §12 の「バースデーテーブル」との関係）。

## 16. 注意事項

- 店舗主催の定例イベントの成功率に関する統計は確認できていない。定例イベントを客足の落ちる時期の集客施策として活用する飲食店の事例は紹介されているが（KURAND SAKE MARKET が毎月多様なイベントを開催するなど）、個々の成果の数字は未確認【二次】。
- 土曜夜の混雑、人数の集まりやすさは**推論**で、検証が必要。
- 評価（確度）は主観の仮置き。検証の結果で更新する。
- 法務の記述は一般論で、専門家の確認を代替しない。
- 事例調査（§12）は、国内の個店の成果を数字で示す公開情報が乏しく、海外の数字はブログ・マーケティング記事の引用で一次情報は未確認。
- 店舗主催が増えない理由（§13.1）と施策の効果は**推論**で、検証（§14）で確認する。
