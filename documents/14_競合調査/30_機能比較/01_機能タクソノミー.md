# 機能タクソノミー(v0.1)

> 関連: [README](../00_README.md) / [機能マトリクス](./02_機能マトリクス.md)(作成後)

イベント告知・集客・コミュニティ系サービスの機能を、サービス間で同じ物差しで比較するための定義。**機能マトリクス(✅一覧)の行**になる。9分類・77機能。

## 1. 使い方

- 機能ごとに「✅の条件」を満たすかをサービス別に判定する。条件は**公式の機能説明・ヘルプ・料金ページ・実機**で確認できたものだけで判定する。
- 確認できないことは❌にしない。**❌は「ない」と確認できたとき**(公式の比較表・FAQ に非対応と明記、実機で確認、など)だけに使い、確認できなければ？にする。
- 機能の有無と「成長への効き」は別である。成長への効きは [有力機能の評価](./03_有力機能の評価.md)(作成後)で、グロースストーリーの根拠と対応づけて評価する。

## 2. 判定値

| 値  | 意味                                                                                               |
| :-- | :------------------------------------------------------------------------------------------------- |
| ✅  | 機能がある(✅の条件を満たす)。根拠を確認済み                                                      |
| △   | 一部のみ、有料プラン限定、特定地域・特定端末(アプリのみ等)限定、条件付き。`note` に条件を書く       |
| ❌  | ないと確認できた                                                                                   |
| ？  | 確認できなかった(根拠なし、情報が古い、非公開)                                                    |

## 3. 根拠レベル

| 値   | 意味                                                           |
| :--- | :------------------------------------------------------------- |
| 公式 | 公式サイト・ヘルプ・料金ページ・公式ブログ・ストア説明で確認   |
| 実機 | 実際の画面・操作で確認(スクショ ID を `note` に書く)           |
| 二次 | 報道・第三者の解説・ユーザーの記事で確認(公式で未確認)         |
| なし | 根拠なし(判定値は？になる)                                     |

## 4. データの置き場所と書式

サービス別の判定は `data/<service>.csv` に置き、機能マトリクスはそこから生成する(手で表を直さない)。

```
feature_id,verdict,evidence_level,evidence_url,note
DS01,✅,公式,https://example.com/help/search,キーワードとカテゴリで検索できる
OP04,△,公式,https://example.com/pricing,有料プランのみ
```

- `feature_id` は本書のIDを使う。77行すべてを書く(確認できなければ `？` と `なし`)。
- `evidence_url` は1つ。複数あれば最も直接的なもの。`実機` のときは空でよい。
- `note` にカンマを含めるときはダブルクォートで囲む。

対象サービスの識別子(`<service>`): `eventbrite` `meetup` `dice` `ticket-tailor` `luma` `partiful` `posh` `peatix` `doorkeeper` `connpass` `kokucheese` `street-academy` `timeleft` `eatwith` `pie` `shokujii`(自社)

自社(`shokujii`)の判定値は次のとおり読み替える: ✅=本番で利用可能、△=一部実装または計画あり(Issue・仕様書IDを `note` に)、❌=なし、？=確認不可。`evidence_url` にはリポジトリ内の文書パスまたはコードのパスを書く。

## 6. 改訂ルール

- 機能を追加・変更したら版を上げ(v0.2 …)、変更点を末尾に記録する。IDは**変えない**(削除したIDは欠番にする)。
- 機能は「ユーザーに見える挙動」で定義する。内部実装や運営ルールは、見える形で提供されているときだけ✅にする。

## 7. v0.2 の改訂候補(未反映)

v0.1 での判定中に、77機能では表せなかったものを記録する。反映するときは版を上げ、新しいIDを末尾に足す(既存のIDは変えない)。判定値の再取得が必要になるため、まとめて行う。

| 候補                                   | 理由                                                                                       | 由来                       |
| :------------------------------------- | :----------------------------------------------------------------------------------------- | :------------------------- |
| 参加者向けの有料プラン・サブスク       | MN02 は主催者向けの定義のため、Timeleft の主収益(参加者向けサブスク)を表せない           | 食事ソーシャルの判定       |
| 卓編成・マッチング(アンケートで同席者を決める) | 食事会の成否に関わる機能だが、対応する行がない。Timeleft の少人数卓とアンケート編成        | 食事ソーシャルの判定       |
| 同席者の相互評価                       | 信頼・継続に関わるが、CR06 は主催者・店舗の評価が前提                                      | 食事ソーシャルの判定       |
| 席のみ確保(支払いは店へ)の送客形態   | FD05 は席・貸切の確保だが、「店に報酬を払わず通常営業の枠に卓を確保する」形態を区別できない | 食事ソーシャルの判定       |
| 参加者から主催者への転換導線           | 成長の根拠が強い経路だが、機能として行がない(参加後ページの「自分もイベントを作る」等)   | 有力機能の評価(機能一覧の外) |
| 営業・伴走(地域コーディネーター等)   | 機能ではなく施策のため v0.2 では対象外とし、施策カタログ側で扱うかを決める                  | 有力機能の評価(機能一覧の外) |
