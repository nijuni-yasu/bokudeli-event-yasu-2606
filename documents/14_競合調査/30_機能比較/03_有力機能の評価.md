# 有力機能の評価:成長に効く機能はどれか

> 関連: [README](../00_README.md) / [機能タクソノミー](./01_機能タクソノミー.md) / [機能マトリクス](./02_機能マトリクス.md) / [グロースストーリー](../10_概観/02_グロースストーリー.md)
> 調査日: 2026-10-11。新しい Web 検索は行わず、機能マトリクスと `data/*.csv`、グロースストーリー、参加者獲得・主催者獲得の2文書に書かれた事実と URL だけで評価した。

本書は「イベント告知・集客・コミュニティ系サービスの機能のうち、参加者獲得・主催者獲得に有力なものはどれか」に答える。機能の有無(標準装備か差別化か)と、成長への効きの根拠の強さを**別の軸**で評価し、Shokujii の現状(自社の穴・強み)と突き合わせる。後続の「機能開発の優先度意思決定」(別文書)への入力であり、**優先度・工数・金額は断定しない**。[事実] は出典に書かれたこと、[推測] は評価者の判断である。「根拠の強さ」と「位置づけ」の判定はすべて [推測] である。

## 要約

**結論: 77機能のうち、正の方向で成長への根拠が「強」と言える機能は一つもない。** 強い根拠があるのは AC01(無料イベントへの課金で悪化した Eventbrite、負の方向)と、機能一覧の外にある「供給側への個別アウトリーチ」「参加者→主催者の経路」だけである。77機能の内訳は、正の根拠が中=9、弱=31、負(導入して悪化した事例)=2、根拠が見つからない=35である。「有力」と言える機能の大半は、複数サービスが同じ方向の説明をしているが、数値は自社主張か二次情報、という水準にとどまる。**普及度の高さは根拠の強さと結びつかない**: 標準装備(競合✅が8以上)の34機能のうち根拠が中以上は3機能(9%)、普及度が4以下の23機能でも3機能(13%)である。

**有力と言える機能・要因(上位10前後)。** 順位は根拠の強さ、採用サービスの多さの順で、優先度ではない [推測]。

**標準装備として「無いと不利」と評価した機能 [推測]。** 競合✅が8以上の34機能で、参加の基本導線(JN02 簡易ログイン13、JN09 リマインド11、JN08 カレンダー10)、共有と社会的証明(SH01〜SH03・SH06)、主催者運用(OP11 主催者ページ14、OP03 下書き12、OP08 当日運営11、OP01・OP06・OP07)、信頼と収益化(TS04・MN01・AC06・MN04)、発見の基礎(DS01・DS06〜DS08)である。ただし根拠は中3・弱14・なし17で、**標準装備であることは成長に効く証拠ではない**。

**自社の穴と強み。** 標準装備34機能のうち自社が ✅ なのは22機能(境界ケース5件を厳密に読むと17機能)で、穴は12機能(DS01・DS02・DS06・DS07・JN04・JN10・SH03・OP08・OP09・OP10・TS03・MN04)である。このうち根拠が中以上なのは DS07 のみ(弱が DS02・JN04・SH03・OP10 の4、なしが7)。根拠が中以上の正の機能9件(AC08・CR01・CR02・DS04・DS05・DS07・FD03・MN03・SH02)では、自社が ✅ なのは5件(CR01・CR02・DS05・FD03・SH02)で、穴は DS04・DS07・MN03・AC08(確認不可)である。強みの FD 系(FD01・FD03・FD04・FD07・FD08)は競合✅が0〜1で差別化の余地は確認できるが、**成長への根拠は FD03(中・他市場)以外は弱またはなし**であり、「競合に少ない」は「成長に効く」を意味しない。

**本書は優先度の結論を出さない。** 検討候補は「後続の意思決定への入力」に、(i) 根拠が中以上で穴のもの、(ii) 差別化の候補、(iii) 根拠は弱いが試しやすそうなもの、(iv) 避けるべき失敗パターンに分けて整理した。

## 評価の物差し

評価は三つの軸を**別々に**つける。普及度は事実、根拠の強さと位置づけは評価者の判断 [推測] である。

**(a) 普及度**は、競合15サービスのうち ✅ の数である(機能マトリクスの「競合✅」の値)。△ は含めない。？ は「確認できなかった」であって非対応ではないため、**✅ 数は下限**である(特に Pie は？が52件)。以下の区分を使う: 標準=8以上(過半数。マトリクスの自動集計と同じ)、準標準=5〜7、低=4以下。

**(b) 成長への根拠の強さ**は、機能の有無とは独立に、「その機能がある(あった)サービスの参加者・主催者の増加と結びつける記述があるか」で決める。

| 強さ | 定義 | 補足ルール(評価者の判断) |
| :-- | :-- | :-- |
| 強 | 創業者・経営陣が因果を認めた、または指標の変化が数値で示された | 10-K・株主レター等の一次開示か自前計測による数値、または経営陣が機能(施策)と指標の因果を特定して認めたもの。出典が「他施策と切り分け不能」と注記したもの、自社主張のみの数値、「口コミが主因」のように機能を特定しない創業者談は強にしない |
| 中 | 複数サービスで同じ傾向が見え、時期的な相関がある | 数値または当事者の説明が複数のサービスにあること。1社でも一次開示の数値があるが切り分けられていないものを含む |
| 弱 | 単一サービス・自社主張・時期的な相関のみ | 数値のない創業者・CEO 談(機能を特定しないものを含む) |
| なし | 根拠が見つからない | 「効かない」という意味ではない。機能の宣伝や仕様の記述だけの場合も「なし」とする |
| 負 | 導入して悪化した事例 | 括弧内に、その因果の強さ(強・中・弱)を書く |

同じ証拠連鎖(CR02・DS05・CR01・OP07 など)は独立した根拠として数えない。根拠が対象15サービスの外(OpenTable・Zeffy 等)にあるときは、その旨を書く。出典間で数値が食い違うときは併記する。グロースストーリー(GS)自身の因果の強さ(強・中・弱)は参考にしたが、本書の定義で付け直した。

**(c) 位置づけ**は次の4種類で、いずれにも当てはまらないものは「—」または「該当なし」とする。

| 位置づけ | 定義 |
| :-- | :-- |
| 標準装備 | 普及度が高く、無いと不利と評価したもの |
| 差別化 | 普及度は低いが、伸びたサービスが武器にしたもの |
| 食事固有 | FD 系(食事・店舗連携) |
| 供給側の誘因 | AC 系(主催者獲得の仕組み)。AC06 のように普及度が高いものは「標準装備(供給側の誘因)」と併記する |

普及度と根拠の強さの分布(77機能)は次のとおりで、**普及度の区分によって「中」の件数は変わらない**。正の方向で「強」の機能は0件である。

| 普及度の区分 | 機能数 | 中 | 弱 | 負 | なし |
| :-- | --: | --: | --: | --: | --: |
| 標準(8以上) | 34 | 3 | 14 | 0 | 17 |
| 準標準(5〜7) | 20 | 3 | 6 | 2 | 9 |
| 低(4以下) | 23 | 3 | 11 | 0 | 9 |

**自社の欄**は機能マトリクスと同じ読み方である: ✅=コードで実装を確認(`origin/main` v2.14.0)、△=一部実装または仕様書・Issue がある、❌=実装も仕様もない、？=確認不可。`*` は、厳密に読むと判定が変わりうる境界ケース15件(自社の調査ノートによる)である。

## 分類別の読み

**発見(DS)。** 数値が出ているのは DS04・DS07 の自社開示(Eventbrite 30%超、DICE 41%、Peatix 約15%)に限られ、いずれも公開イベントの在庫が厚いことが前提になる [推測]。検索・絞り込み・保存(DS01・DS03・DS06)は普及度6〜11だが、成長に結びつける記述は見つからなかった。DS02 の根拠は地図 UI ではなく、Meetup・Timeleft・당근の「エリア単位で密度を作る」設計である。負の事例は Timeleft の小都市での縮小で、Google のイベント構造化データの対応言語に日本語の記載がない点も留意が要る。

**申込(JN)。** 成長に効いたと説明されるのは JN01(アカウント不要)だが数値はなく、アカウント必須の Meetup・DICE・Posh・Peatix・connpass も成長している。JN04 は DICE・Fever の自社主張で、JN09 の出席率改善値は全サービスで見つからなかった。JN02・JN06〜JN08・JN10〜JN12 は標準装備だが根拠なしである。明確な負の事例はなく、こくちーずの会員登録必須化(2023-04)の影響は測れていない。

**共有(SH)。** 数値があるのは Eventbrite の共有1回あたり売上(2010年)だけで、Partiful・Luma は口コミを主因と言うが、紹介経由の比率・k-factor はどのサービスも非公開である。Posh の Kickback と Luma の Event Referrals(SH04)は紹介を可視化するが、成長への寄与は不明。OGP・QR(SH01・SH07)は根拠なし。外部ソーシャルグラフへの依存(SH05)は、Meta の Events API 閉鎖(2018)のように断たれうる。

**主催者運用(OP)。** 12機能のうち10機能が標準装備で、最も揃っている分類である。成長への根拠は薄く、OP01 は複数サービスが牽引機能と説明するが因果は不明、OP10 は Meetup Pro の自社主張、OP12 は Ticket Tailor の Wix・WordPress 連携のみで、OP02〜OP06・OP08・OP09 は根拠なしである。「無いと選ばれない」水準の標準装備であって [推測]、主催者獲得の決め手になった証拠は見つからなかった。

**主催者獲得(AC)。** 根拠が最も強い分類だが、強いのは機能というより経済条件と人的施策である。AC01 は負(強)、AC08 は中(負あり)で、機能一覧の外の個別アウトリーチは強である。AC05(紹介報酬)は複数サービスが採用するが Ticket Tailor では効かず、AC04・AC06・AC07 は弱い。AC06 は普及度13でも根拠は弱く、ストアカの地域コーディネーターのような人的な伴走のほうが根拠は強い。

**継続(CR)。** 再訪・告知に効く CR01・CR02 が中で、複数サービスで方向が一貫している(数値は自社主張か二次)。CR04〜CR07 は弱で、CR07 は「チャット」ではなく「卓編成」が効いたと説明されている。CR03・CR08 は根拠なしで、負の事例は見つからなかった。

**信頼(TS)。** 成長への根拠はほぼ見つからない。TS04 は普及度11の標準装備で、事前決済・欠席対策は食事会で重要になる [推測] が、成長との関連を示す数値はない。TS02・TS06 はストアカの安心設計が成長の説明に使われる一方、外部誘導の禁止や重い審査は不満や裾野の縮小を招くという指摘(数値なし)がある。

**食事(FD)。** 競合✅は FD09(5)・FD05(3)を除き0〜1で、差別化の余地は確認できる。成長への根拠は、対象外の飲食店SaaS に基づく FD03(中)と、ベンダー自己申告の FD01・FD04(弱)にとどまる。Timeleft の卓確保(FD05)は拡大に寄与したと説明されるが、店への対価なし・注文しない参加者による店の離脱、広告拡大後の縮小という負の面を伴う。

**収益化(MN)。** MN01 は標準装備(13)で、総額表示は転換の説明(RA の +3〜5%、検索要約)がある一方、不透明な手数料表示は訴訟になった(Posh)。MN02 は負(中)で、Meetup と Eventbrite の供給側課金が離脱を招いた。MN03 は NPO・協会市場で中、MN04・MN05 は根拠なしである。

## 後続の意思決定への入力

以下は検討候補であり、順序は優先度ではない。各項目の末尾に、決めるべき論点を1行で付ける。

**(i) 根拠が強い・中で、自社が穴または範囲が限られるもの**

- **DS07 都市×カテゴリの公開面**(中、△)。論点: 日本語の検索需要と Google の対応が不確かな中で、仕込み済み SEO の刈り取り(D0)と並行掲載(P4-1)の結果を待つか、先にハブを作るか。
- **DS04 発見・推薦**(中、△)。論点: 公開イベントの在庫が少ない段階で、推薦・related に出せる件数が足りるか(在庫の閾値をどう置くか)。パーソナライズ前に「今週開催」「近くの食事会」で検証するか。
- **CR01・DS05・CR03 通知の範囲拡大**(中、✅ だが限定的)。論点: 公開イベントの発見面をどこまで広げるか(社内の安心感との境界。露出獲得施策の未決事項 #5・#6)と、配信停止率・開封率の計測をどう置くか。
- **AC08 運営主催・公式イベント**(中・負あり、？)。論点: 運営の公式イベントの実績を台帳化するか。固定費を持たない範囲(Dinner Lab との違い)をどこに置くか。
- **供給側への個別アウトリーチ・伴走**(強、機能外)。論点: 人手を投入するエリア×属性の単位と、成果の指標(幹事の2回目開催率など)をどう置くか。
- **参加者→幹事の導線**(強・経路の存在、機能外)。論点: 転換率を測れる形(完了後の CTA か、参加回数上位への打診か)で入れるか。公開値がないため自社計測が前提。
- **定期・会員(S-08)**(中・自己申告、機能外)。論点: コミットメントを課す定期注文の返金・決済設計と、外部ショック時の解約集中(트레바리の会員75%減)への備え。

**(ii) 差別化の候補**

- **FD 系(FD01・FD03・FD04)を店舗側の供給獲得の入口として使う**(根拠は FD03 が中、他は弱)。論点: 店にとっての単体価値(仕込み数の把握・no-show 抑制)を営業材料にするとき、どの指標で検証するか。
- **FD02 アレルギー・食の好み**(競合✅0、自社 ❌、根拠なし)。論点: 成長のためではなく信頼・安全のための機能として扱うか。

- **SH04・AC05 紹介の可視化と報酬**(弱、❌)。論点: Luma 型の可視化だけを先に入れるか。報酬型は原資・返金時の扱い・不正対策・法務(未決事項 #3)が前提で、Ticket Tailor では効かなかった。
- **AC04 競合の撤退・値上げ時の移行**(弱、❌)。論点: connpass の有料化(2026-11)や Meetup の値上げを機会にするとき、取り込み機能なしで手動の並行掲載や移行手順の案内で足りるか。

- **SH02 の文面・UTM・押下率の計測**(D1-1・D6-4・D6-5)。論点: 他社に定量値がない領域のため、自社の計測で根拠を作る。共有→申込の指標を先に決められるか。

**(iv) 避けるべき失敗パターン(負の事例)**

- **幹事への課金・無料イベントへの課金**(AC01・MN02。Eventbrite・Meetup)。論点: 収益を注文側に寄せるとき、幹事の入口(無料)を侵さない境界をどこに置くか。
